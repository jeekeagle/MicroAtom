# Agent as a Service：微课制作产品的设计方法论

> 本文是「课序 KEXU」的设计底稿。它回答一个问题：一个微课制作产品，应该如何按
> "Agent as a Service（AaaS）"的理念从零构建，而不是在传统表单界面后面藏几个大模型调用。
>
> 文中所有抽象都能在本仓库里找到对应实现，不是纸面设想。

---

## 一、核心命题：智能体不是功能，而是服务层

### 1.1 两种产品的分水岭

绝大多数"AI 微课产品"长这样：

```
教师填表单 → 点"AI 生成" → 后端拼一段 prompt → 调 LLM → 把结果塞回页面
```

这种做法的问题是：**智能体被焊死在某个按钮后面**。换模型要改代码，加一个环节要改
界面，换一种课程模式要重写流程。AI 是一层皮，产品骨架还是二十年前的表单软件。

按 AaaS 理念，产品应该长这样：

```
每一个生产环节 = 一个有契约、可替换、可组合、可观测的智能体服务
工作流 = 这些服务的编排图
界面 = 编排图的一个可视化视图
CLI  = 编排图的另一个调用入口
```

### 1.2 一个可操作的判断标准

> **把模型换掉、把智能体换掉、把某个环节的实现换掉——如果产品骨架不用动，
> 那它就是服务化了；如果要动，说明智能体还只是功能。**

这条标准贯穿本文后面所有的设计决策。

---

## 二、五层服务架构

微课制作被拆成五层，每层只依赖下一层的契约，不依赖实现。

```
┌─────────────────────────────────────────────┐
│  L5 产品层   界面 / CLI / 交付物              │
├─────────────────────────────────────────────┤
│  L4 工作流层  环节 DAG + 依赖 + 人工确认点     │
├─────────────────────────────────────────────┤
│  L3 引擎层    同一环节的可替换实现             │
├─────────────────────────────────────────────┤
│  L2 智能体层  有角色/记忆/工具的 Agent         │
├─────────────────────────────────────────────┤
│  L1 原子能力层 Skill（最小可复用单元）         │
└─────────────────────────────────────────────┘
```

### 2.1 L1 · 原子能力层（Skill）

Skill 是系统里最小的、可独立调用的能力单元。它有三特征：

- **单一职责**：一个 Skill 只做一件事。例如 `concept-scan` 只扫描全文抽概念，
  `qa-author` 只把概念写成问答，`slide-whiteprint` 只做白底课件的版式设计。
- **可独立试运行**：Skill 库里每一个都能单独跑，不依赖课程上下文。这是可测试性的来源。
- **可被多个智能体共享**：`card-compose` 既被"构页"调用，也被"介质工坊"调用。

> 为什么必须有这一层？因为**Skill 是能力，智能体是角色**。把能力直接写进智能体，
> 就等于把函数写进类里不抽出来——换一个角色就得复制一遍能力。Skill 层让能力可以
> 跨角色复用，也让"新增一种介质"的成本从"改智能体"降到"加一个 Skill"。

### 2.2 L2 · 智能体层（Agent）

智能体是**角色化的编排单元**：它有自己的职责边界、可以读取的记忆、可调用的 Skill 集合，
以及一段稳定的角色说明。本系统里的例子：

| 智能体 | 职责 | 典型调用的 Skill |
| --- | --- | --- |
| 析课 | 分析备课意图、优化课程结构与价值主线 | 意图分析、结构规划 |
| 构页 | 把讲稿变成图文并茂的课件页面 | slide-whiteprint / slide-interactive、视觉图层 |
| 声场 | 生成旁白、处理转写与音画对齐 | TTS、ASR、时间轴对齐 |
| 校尺 | 评审讲稿与课件质量 | 质检、一致性检查 |

关键设计：**智能体不直接碰模型**。它声明"我要做什么"，由引擎层决定"用哪个模型、
哪套 prompt、什么参数去做"。这样智能体可以在不同引擎下复用。

### 2.3 L3 · 引擎层（Engine）—— 解耦的关键层

引擎是 AaaS 在本产品里最核心的抽象。**同一个生产环节可以有多个引擎，每个引擎绑定
一组智能体 + Skill + 模型档位**，系统按配置选择用哪个。

以"课件生成"为例，系统里同时存在多个引擎：

- 结构课件引擎：按教学结构模板排版，稳定、快、便宜
- 文字课件引擎：以文字叙述为主，适合文科
- 白底课件引擎：调用 `slide-whiteprint`，产出白底编辑风课件
- HTML 课件引擎：调用 `slide-interactive`，产出带交互的 HTML 课件
- 文生图课件引擎（规划中）：调用图像模型配图

同样，"析课""讲稿""旁白""成片"每一个环节都有自己的默认引擎，也都能新建引擎。

> **引擎层的真正价值**：它把"这个环节用什么实现"从代码里搬到了配置里。
> 教师或管理员可以在界面上新建一个引擎、挂上自己的智能体，立刻改变这个环节的行为，
> 不需要任何一次代码发布。这就是"可开发的产品"的含义——**产品本身是可被配置开发的**。

### 2.4 L4 · 工作流层（Workflow）

工作流把环节组织成有向图，声明依赖关系和人工确认点。系统内置三种默认工作流，
对应三种课程模式：

| 模式 | 环节路径 | 特点 |
| --- | --- | --- |
| 全自动 | 主题 → 讲稿 → 确认 → 课件 → 旁白 → 成片 | AI 推进到底，只在关键点人工确认 |
| 口语稿驱动 | 口述 → 转写/对齐 → 课件 → 合成 | 教师先自由讲，系统按语音定位页面 |
| PPT 驱动 | 讲稿 → 课件 → 试讲录制 → 对齐 → 成片 | 教师对照课件讲，系统录音录屏 |

关键设计：**工作流也是配置，不是代码**。三种模式不是三套写死的流程，而是三份
工作流定义。新增一种模式（比如"翻转课堂模式""实验探究模式"）只需要新增一份定义，
界面和引擎全部复用。

### 2.5 L5 · 产品层

产品层包含教师看到的一切：左侧功能目录、右侧运行抽屉、讲稿工坊、课件工坊、
声音与录制、成片交付、介质工坊、运行设置。

但要强调：**产品层只是编排图的一个视图**。同一份编排，界面上能操作，CLI 也能操作，
外部 Agent 还能操作。产品层没有独占任何能力。

## 三、服务契约：让每个环节可被信任地调用

服务化的核心不是"拆开"，而是"拆开之后还能可靠地组合"。这需要每一环都有契约。

### 3.1 输入 / 输出 Schema

每个环节的输入输出都是结构化的、有类型的。例如"析课"环节的输出契约包含：
课程主题、课程名称、学科、学段、时长、教学设想、价值引领、学情、风格。

Schema 的价值有三个：

1. **可验证**：结果不合契约就能立刻发现，而不是等到渲染时才炸。
2. **可组合**：上一环的输出能被下一环安全地消费。
3. **可被外部 Agent 理解**：`kexu schema --json` 把全部契约机器可读地暴露出去，
   任何 Agent 读一遍就知道怎么调用整个系统。

### 3.2 模型档位解耦（Model Profile）

引擎不绑定模型厂商。系统维护一个"模型连接引擎"：每个档位包含服务地址、模型名、
协议、温度、独立 API Key。任意 OpenAI 兼容服务都能接入，运行时可切换默认档位。

这意味着：**换供应商 = 换一个配置档位**，不改任何智能体或引擎代码。今天用 A 厂商，
明天接 B 厂商的本地部署，产品行为不变。

### 3.3 降级链（Fallback）

服务必须能在依赖失败时优雅降级，而不是把错误直接甩给教师。

本系统的降级链：

```
大模型生成 → 失败 → 本地结构兜底（按模板产出可用草稿）→ 明确告知"这是兜底结果"
```

兜底结果不是"假装成功"，它会标记来源，教师知道这是结构化模板产物、需要自己补充。
**降级的意义是让教师永远能往前走，而不是卡死在一次网络抖动上。**

### 3.4 人工确认点是一等公民

全自动不等于无人值守。工作流里显式声明"哪些环节必须人工确认"，例如讲稿确认。
教师确认后，后续的课件、旁白、字幕才以定稿讲稿为准。

这个设计的理由：**微课的价值判断权在教师手里**。智能体负责生成候选，教师负责拍板。
确认点就是这个权限边界的落点，它必须是工作流的一等结构，而不是界面里的一个临时按钮。

### 3.5 可观测性（Trace & Activity）

每个环节的调用都留下记录：哪个智能体、哪个引擎、哪个模型、耗时、来源
（`model` 还是 `local-fallback`）。系统右侧抽屉里的"智能体动态、运行状态、调度任务"
就是这份数据的可视化。

可观测性不是运维奢侈品——**它是教师信任智能体的前提**。教师要能看到"这一步是谁做的、
花了多久、是不是兜底"，才敢把一节课交给系统。

## 四、记忆即服务（Memory as a Service）

### 4.1 三种记忆，三个作用域

| 记忆类型 | 作用域 | 内容 | 谁读谁写 |
| --- | --- | --- | --- |
| 教师记忆 | 跨课程、长期 | 学科、学段、学校、教龄、教学风格、经验、心得 | 教师维护，所有智能体读取 |
| 项目记忆 | 单课程内 | 讲稿、课件、录音、对齐结果、成片状态 | 流程读写 |
| 环境记忆 | 系统级 | 模型档位、引擎配置、工作流定义、品牌设置 | 管理员维护 |

### 4.2 记忆是横切服务，不是 prompt 里的散落字符串

新手做法是把"教师是物理老师"这句话手动拼进每次的 prompt。AaaS 做法是：
**教师记忆是一个结构化服务，任何智能体在被调用时自动注入它需要的切片。**

这样带来三个好处：

- 教师只维护一次，所有环节受益。
- 记忆可以被界面化编辑（本系统的"教师记忆"页面），而不是藏在代码里。
- 记忆可以演进：以后加入"学生记忆""班级记忆"，只是新增一个记忆服务，
  智能体和引擎都不用改。

### 4.3 新建课程时的记忆服务实例

一个典型场景：教师在新建微课时点录音口述课程设想，说完后一个智能体自动分析，
把课程主题、名称、学科、学段、时长、价值引领全部填好，教师确认即可。

这里发生的是：**语音转写服务 → 分析智能体 → 教师记忆（读取学科/学段偏好）→
结构化字段（写入项目记忆）**。四个服务协作，教师只说了一段话。

## 五、HTML 作为统一交付容器

### 5.1 为什么是 HTML

本系统里，课件是 HTML，知识图谱是 HTML，概念卡是 HTML，一图读懂是 HTML，
时间线是 HTML，问答卡是 HTML，最终的交互式课程还是 HTML。

这不是技术偏好，而是服务化设计的必然结果：

- **HTML 是唯一能同时承载静态排版、动态交互、多媒体、离线分发的容器。**
- 用 HTML 做介质，意味着"新增一种介质"只需要新增一个生成 Skill + 一个卡片渲染器，
  不需要为每种介质发明新的文件格式和播放器。
- HTML 介质可以被嵌入、被链接、被离线打开，天然适配教育场景的分发需求。

### 5.2 从 MP4 到交互式 HTML 课程

传统交付是 MP4：一条时间轴，画面和声音被烧死在一起，讲到"提示词"这个概念时，
学生只能被动看。

本系统的"编辑成片"环节提供另一种交付：

```
上端：播放课程视频与音频
下端：随时间推进，弹出挂载在对应时间点的卡片
交互：点击卡片 → 展开到大窗口 → 查看概念详解 / 问答 / 知识图谱
```

实现前提是**精确的时间轴对齐**：音频轨和逐字稿轨的每一处都能定位，
知道"哪一秒讲到了哪个概念"。基于这个定位，智能体去挂载合适的卡片。

> **这是 AaaS 在交付物上的体现**：视频不再是终点，而是一个可被智能体继续编排的
> 时间轴。卡片是智能体生成的服务产物，挂载是智能体做的决策，展开交互是统一的
> HTML 契约。教师交付的不是一个文件，而是一个可交互的学习环境。

## 六、产品自身也是一个 Agent Service

### 6.1 双向组合

这是 AaaS 理念最有意思的一步：**你的产品既能调用智能体，也能被智能体调用。**

本系统提供完整 CLI：

```bat
kexu.cmd schema --json                     # 读全部命令与输入输出契约
kexu.cmd projects list                     # 查项目
kexu.cmd projects create --topic "..."     # 建课程
kexu.cmd run project-xxx --json            # 跑工作流
kexu.cmd render download project-xxx       # 取成片
```

`kexu schema --json` 把整个系统的能力暴露成机器可读的契约。Codex 或任何外部 Agent
按"读 schema → 查项目 → 执行动作 → 检查状态"的方式驱动整套微课生产线。

### 6.2 这意味着什么

- 教师可以对 Codex 说"帮我做一节《浮力》的微课，全自动，做完把成片路径给我"，
  Codex 读 schema、调 CLI、检查状态，全程不需要人碰界面。
- 教师可以在自己的 Agent 工作流里把"课序"当成一个服务节点：上游接调研 Agent，
  下游接发布 Agent，中间的微课生产是一个黑盒服务。
- 产品可以被另一个产品集成。你的微课生产线，可以成为别人 Agent 平台里的一个工具。

> **判断一个产品是否真的 Agent as a Service，最后就看这一条：
> 它能不能被另一个 Agent 无缝调用。** 能，它就是服务；不能，它只是一个界面。

## 七、演进逻辑：这套骨架为什么撑得住迭代

AaaS 的回报在迭代速度上。用本文的判断标准检验几个真实的变化场景：

| 变化需求 | 服务化的成本 | 不服务化的成本 |
| --- | --- | --- |
| 新增一种课件风格 | 加一个引擎配置 + 一个 Skill | 改界面 + 改后端 + 发版 |
| 新增一种课程模式 | 加一份工作流定义 | 重写一套流程代码 |
| 新增一种教学介质 | 加一个生成 Skill + 卡片渲染器 | 发明新格式 + 新播放器 + 改交付逻辑 |
| 换模型供应商 | 加一个模型档位配置 | 改所有 prompt 调用点 |
| 新增一个生产环节 | 加一个环节定义 + 挂到工作流 | 改工作流代码 + 改界面导航 |
| 接入外部 Agent | 暴露 schema（已内置） | 另写一套 API + 文档 |

可以看到，**服务化之后，绝大多数迭代是"加配置"而不是"改代码"**。这就是为什么这套
骨架能在几轮需求变更里持续演进而没有推倒重来。

## 八、落地红线：什么时候不该用智能体

AaaS 不是"什么都上智能体"。有几条红线必须守住：

### 8.1 确定性操作不要交给智能体

文件读写、音视频转码、页面渲染、时间轴计算、文件打包——这些是确定性任务，
交给确定性引擎。智能体负责**生成与决策**，执行交给工程模块。

让智能体去做"把 MP4 转成 H.264"这种事，是既慢又贵又不可靠的反模式。

### 8.2 每个环节要有成本与延迟预算

不同环节对模型的要求差别很大：

- 讲稿生成、价值主线分析：需要强推理，值得用大模型
- 概念抽取、字段填充：中小模型即可
- 版式微调、格式转换：规则或本地模型即可

引擎层的价值在这里再次体现：**同一个环节可以按预算切换引擎**，便宜的日常用，
贵的留给关键环节。

### 8.3 兜底必须诚实

降级链产出的结果要明确标记来源，不能让教师误以为是大模型精心生成的。
本系统在每个生成结果上标注 `source: model` 还是 `local-fallback`，
就是这条红线的落地。

### 8.4 人工确认点不能省

涉及教学价值判断的环节（讲稿定稿、课程立意、价值引领）必须保留人工确认。
智能体是教师的助手，不是教师的替身。

## 九、产品形态的演进路径

按 AaaS 构建的产品，天然有清晰的演进路径：

```
阶段一：单机工具     教师在界面上操作，智能体在后台服务
阶段二：可编排平台   教师/管理员能配置引擎、工作流、智能体组合
阶段三：服务节点     产品通过 CLI/schema 被外部 Agent 调用
阶段四：服务市场     引擎、智能体、Skill、工作流模板可被分享、复用、交易
```

本系统当前处在阶段二向阶段三过渡：引擎与工作流已可配置，CLI/schema 协议已内置，
教师记忆、模型档位、介质工坊等服务化组件都已就位。

下一阶段的机会在于**把"配置"变成"资产"**：一位物理老师沉淀的课件引擎、
一位语文老师沉淀的讲稿智能体，都可以成为可复用、可分享的服务模板。
那时产品就不再是"一个微课工具"，而是"一个微课服务的运行时"。

## 十、结语

回到最初的问题：如何通过 Agent as a Service 的理念设计微课制作产品？

答案可以压缩成三句话：

1. **把每个生产环节做成有契约的服务，而不是界面上的一个按钮。**
2. **把"用什么实现"从代码搬到配置，让产品可以被配置开发。**
3. **让产品自己也能被 Agent 调用，成为别人服务链里的一个节点。**

做到这三条，微课制作产品就不再是一个会被下一个 AI 浪潮淘汰的工具，
而是一个能持续吸收新技术、持续被复用的**服务运行时**。
